# IPTV platform — модель PostgreSQL v1.0

**Статус:** исходный DDL/первичные миграции для нового проекта. Предусматривается PostgreSQL **14+** (рекомендуется PostgreSQL 16/17). Миграции рассчитаны на **пустую выделенную БД** и исполняются строго по порядку. Не следует применять к существующей БД без предварительной проверки.

## Зафиксированные решения

1. Общие каналы/жанры/плейлисты; `visibility` = `all|selected` и таблицы связей с провайдерами.
2. `catalog.streams` — логический канал; `catalog.stream_sources` — несколько отдельных источников `live`/`dvr`, глобальных или специфичных для провайдера; минимум приоритета = основной.
3. `catalog.app_types` (TV, CCTV, домофония, радио) и `catalog.genres` (эфирные, спорт, кино...) — разные сущности; у потока один app_type и несколько жанров.
4. `streams.is_paid` не существует. `streams.is_public` = разрешение гостевого просмотра; `playlists.is_public` = публичность каталога. Цена плейлиста может быть информационной; расчёт и подтверждение оплаты у внешнего биллинга.
5. Администраторы `auth.users` (локальная учётная запись и/или OIDC); зрители `subscribers.abonents` — отдельные сущности.
6. Терминал идентифицируется `device_uuid`, присылаемым клиентом; уникальность UUID гарантирована в **пределах установки и действующей БД**, но физическое устройство не идентифицируется криптографически.
7. Лимиты терминалов определяются `core.providers.default_terminal_limit` и необязательным `abonents.terminal_limit_override`. `NULL` — наследовать, `0` — без ограничения. Активный терминал — включённый и привязанный к абоненту.
8. Лимиты параллельного просмотра определяются аналогично `default_concurrent_stream_limit` / `concurrent_stream_limit_override`, но требуют атомарных lease-записей в Redis (или эквивалентном хранилище) на стороне NestJS. **Не следует подсчитывать строки истории просмотров как активные сессии**.
9. `providers.playback_history_enabled=false` по умолчанию: не записывать подробную историю просмотров в PostgreSQL при высокой нагрузке. Для ограничения одновременных просмотров достаточно краткоживущих leases, не исторической записи каждой операции.
10. Система сообщений, EPG и мониторинг источников заложены в таблицах. Модуль VOD и жалобы будут добавлены миграциями в последующих этапах; схемы `vod` и `support` уже существуют, таблиц там пока нет.
11. Непосредственное ограничение доступа к HLS/UDP на медиасервере **отложено**. Предоставляемые клиентам прямые URL пока могут быть использованы вне приложения — это сознательное ограничение первой версии.
12. Переключение на облачный сервер не должно быть обязательным при работоспособном локальном DNS/backend. Данные локальных установок не синхронизируются автоматически.

## Миграции

| Файл | Содержимое |
|---|---|
| `0001_core_auth_audit.sql` | Схемы, установка, провайдеры, администраторы, OAuth/OIDC, права и роли, аудит |
| `0002_catalog.sql` | Типы приложений, жанры, каналы, LIVE/DVR, мониторинг, плейлисты и правила доступности |
| `0003_subscribers.sql` | Абоненты, назначения, терминалы, лимит терминалов, сессии, избранное, parental, просмотры |
| `0004_epg.sql` | Источники, языки, каналы, передачи, привязки, загрузки |
| `0005_messaging.sql` | Уведомления, адресаты, расписание, запуск и журнал доставки |
| `0006_seeds.sql` | Справочники типов приложений, набор разрешений, начальные роли и настройки |

Каждая миграция выполняется внутри отдельной транзакции и регистрирует свою версию в `core.schema_migrations`. Если внутри файла возникает ошибка, транзакция откатывается целиком.

### Применение

```bash
createdb iptv_dev
export DATABASE_URL='postgresql://iptv_admin:CHANGE_ME@127.0.0.1:5432/iptv_dev'
./scripts/migrate.sh
```

`iptv_admin` должен иметь права на создание схем и таблиц в выделенной БД. Первый административный аккаунт создаётся отдельной bootstrap-командой backend (пароль только через Argon2id); seed **не создаёт** пользователя с известным паролем. Запускайте мигратор одним процессом при развёртывании, до старта нескольких экземпляров NestJS.

Просмотр применённых версий:

```sql
SELECT version, applied_at FROM core.schema_migrations ORDER BY version;
```

Разрушительный откат только для свежего DEV:

```bash
CONFIRM_DESTROY=yes ./scripts/rollback.sh
```

**Внимание:** rollback удаляет ВСЕ перечисленные схемы и их данные, а не делает безопасный downgrade. Для PROD потребуются адресные миграции `ALTER TABLE` и предварительные бэкапы.

## Бизнес-логика, остающаяся в NestJS

- Проверка прав администратора одновременно по действию и списку провайдеров, включая операции по ID; глобальные объекты нельзя менять оператору провайдера напрямую. `role.provider_id=NULL` даёт глобальную область только после явного назначения привилегированным администратором.
- Внешняя OAuth/OIDC-идентичность `(issuer, subject)` создаёт пользователя в `pending`, без назначенных ролей. Нельзя доверять одному email для автоматического связывания.
- Абонентские пароли: `password_hash` для проверки (Argon2id), `password_ciphertext` в формате **AEAD**, например nonce+ciphertext+tag AES-256-GCM. `password_key_id` выбирает ключ из защищённой среды **вне БД**. Дешифрование допускается только при `abonents.credentials.read`, с аудитом каждого обращения и маскированием в логах. Никогда не передавать ключ в дамп, REST или аудит. Если просмотр оператором не нужен, достаточно хранить один хеш и дать сброс пароля.
- Глобальный ресурс с `visibility=selected` и без связей провайдеров недоступен никому. Добавление и удаление связей проверяется в API, включая конфликт назначенных плейлистов/каналов. Выданные ранее права **не обходят** актуальную доступность провайдеру.
- В `catalog.stream_sources` выбирается источник нужного `source_kind`, сначала специфичный для провайдера (при наличии подходящего), затем глобальный; по возрастанию `priority`. Состояние источников влияет на выбор резерва. Проверки UDP требуют специализированного probing, не только HTTP HEAD.
- Для DVR `url` содержит URL или URL-шаблон; `dvr_url_mode='template'` разрешает только задокументированные плейсхолдеры `{start_unix}`, `{end_unix}`, `{duration_sec}`, `{start_iso}`, `{end_iso}`. Шаблон разворачивается только на backend; данные EPG должны быть валидны. Не выдавать приватные/административные адреса и ключи в клиентских конфигурациях.
- Номер канала по умолчанию хранится в `streams.number`; для конкретного провайдера допускаются `stream_provider_overrides.number_override`. Порядок каналов в плейлисте независимый (`playlist_streams.position`). При перестановке используйте `SET CONSTRAINTS catalog.playlist_streams_position_uq DEFERRED` внутри транзакции.
- Для сессий терминалов хранить только хеш refresh-токена, `expires_at` и `revoked_at`, не сам токен. При входе абонента проверять `enabled`, наличие места для терминала, провайдера и родительские настройки. Ограничение по числу терминалов обеспечено PostgreSQL-триггером на `terminals`; валидация провайдерской принадлежности плейлистов/потоков — на INSERT/UPDATE в таблицах назначений.
- При изменении провайдера абонента следует отдельно переоценить назначения, устройства и историю; не менять `abonents.provider_id` напрямую в админке без процедуры перевода.
- Активность просмотров: проверяемые атомарно leases, например `playback:{provider_id}:{abonent_id}` с TTL 90 сек и heartbeat 30 сек. Для безопасности от гонок при одновременном старте — Redis Lua/transaction. **Ограничение пока действует на уровне API/официального клиента, без защиты HLS-URL не защищает от стороннего плеера.**
- `terminal_settings.settings` — ограниченная схема JSON (локаль, тема, настройки плеера), проверяется валидатором. Избранное нормализовано отдельно.
- Родительский контроль: server-side фильтрация с учётом `stream.is_adult`, `stream.age_rating`, `genre.is_adult` плюс клиентский PIN/UX. Без проверки на медиасервере не гарантируется защита от просмотра прямого HLS URL.
- EPG: загрузка `.xml`/`.xml.gz` с URL либо ручная загрузка файла в object storage (`upload_object_key`), ограничение размера, удалённые источники защищать от SSRF, нормализация UTC, сопоставление с каналами, чистка истёкших записей. Рекомендована загрузка XMLTV потоковым парсером, а не целиком в память.
- Динамические фильтры рассылок задавать только валидированным JSON AST в `messaging.audiences.rules`; запрещено подставлять клиентский SQL. При запуске кампании заново рассчитывать получателей и контролировать свежесть снимка баланса. Дедупликация отправок, частота показа и отправка через WebSocket/polling — в сервисе.
- Административный аудит писать в той же транзакции, что и изменение. Чувствительные значения из полей `audit.events.details` удалять до записи.
- Таблицы `auth.user_sessions`, `terminal_sessions`, `messaging.deliveries`, `epg.programmes`, `source_health_events` и опциональные `playback_sessions` потребуют задач TTL/retention, лимитов и наблюдения за размером.
- RabbitMQ и интеграционные контракты не включены в начальные миграции; позднее добавим отдельную outbox/inbox-схему с идемпотентностью обработки сообщений от биллинга и наружных событий об авариях.

### Пример правил рассылки

```json
{
  "and": [
    {"provider_ids": [3]},
    {"balance_lt_kopecks": 10000},
    {"abonent_enabled": true},
    {"platforms": ["android", "web"]}
  ]
}
```

**Это контракт будущего сервиса**, не готовый SQL-фильтр. JSON не компилируется автоматически самой БД.

## Ограничения первого этапа

1. Система **не содержит готового NestJS API и бизнес-логики**. SQL — фундамент, не полностью работающая платформа.
2. Проверки динамических операций с каталогом, авторизация по областям провайдеров, приоритеты источников и расчёт лимита параллельного воспроизведения ещё реализуются в сервисах.
3. `support`/`vod` — пустые схемы: таблицы жалоб и видеотеки создадим позже.
4. Перед применением к PROD обязательны интеграционные тесты на работающем PostgreSQL. SQL подготовлен и статически проверен, но в среде генерации не было запущено живого PostgreSQL для выполнения миграций.
5. Если необходимо поддержать PostgreSQL 13 или более старый сервер, потребуется отдельная проверка совместимости синтаксиса и функций.
