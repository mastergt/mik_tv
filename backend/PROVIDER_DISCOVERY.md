# mik_tv — автообнаружение провайдера по IP

**Единый стартовый адрес:** `https://start.iptv.artelmik.ru`. Прежняя IPTV-система не используется.

При запуске Android-клиент обращается к `GET https://start.iptv.artelmik.ru/api/v1/client/discover`.
Ответ при совпадении IP-подсети:

```json
{
  "api_version": 1,
  "api_base_url": "https://start.iptv.artelmik.ru/api/v1",
  "provider": {"id": 5, "slug": "mlink", "name": "Мегалинк"},
  "match": "network"
}
```

Если ни одна сеть не совпала, используется **единственный активный провайдер** с `is_default=true`.
Тогда `match="default"`. При отсутствии активного default возвращается **404**:
`{"code":"PROVIDER_NOT_FOUND","message":"Provider not found for client IP",...}`.
В bootstrap для старых клиентов оставлен список провайдеров, но **регистрация терминала проверяет provider_slug на соответствие определённому по IP провайдеру**. Подмена провайдера в ручном запросе приводит к 403.

## Подсети и приоритет

В админке «Провайдеры → Редактировать» есть текстовое поле «IP-подсети», по одной записи на строку: например, `198.51.100.0/24`, `203.0.113.44/32`, `2001:db8:abcd::/48`. Адреса без маски нормализуются в /32 или /128. Вложенные подсети разрешены: **самая длинная маска выигрывает** (точный /32 приоритетнее /24). Точное совпадение CIDR в базе уникально даже между провайдерами. При редактировании список заменяется атомарно; старые данные сохраняются при ошибке. Все запросы на редактирование требуют глобального `providers.write`.

В системе одновременно может быть **только один** provider по умолчанию (частичный уникальный индекс PostgreSQL). При выборе нового старый флаг сбрасывается в той же транзакции. Выключенный провайдер не участвует в выборе.

## Настройка backend на DEV/PROD

1. Обновить backend и frontend из Git. Новый код backend не запустит discovery без миграции.
2. Применить миграцию (не сбрасывает существующих провайдеров):
   ```sh
   cd /usr/local/nodejs/dev/iptv_front/backend
   # DATABASE_URL берётся из уже настроенного .env:
   set -a
   . ./.env
   set +a
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f database/migrations/0010_provider_discovery.sql
   ```
3. В `backend/.env` **добавить**:
   ```ini
   CLIENT_PUBLIC_API_URL=https://start.iptv.artelmik.ru/api/v1
   ```
   Других переменных менять не требуется. Это публичный HTTPS-адрес, возвращаемый в ответе клиента. Если не указан, используется этот же адрес по умолчанию.
4. Настроить DNS A/AAAA `start.iptv.artelmik.ru` на нужный сервер, выдать TLS-сертификат и добавить nginx block из `backend/nginx.start-iptv.example.conf`. В нём X-Real-IP всегда **перезаписывается** значением `$remote_addr`; NestJS слушает только localhost. Если перед nginx стоит другой прокси/CDN, нужно отдельно настроить `set_real_ip_from` **только для доверенных адресов**. Иначе backend увидит адрес самого CDN.
5. Пересобрать backend и frontend, перезапустить соответствующие процессы штатным способом. Для NestJS: `npm run check && npm run build`, затем PM2 reload/restart API.
6. В админке назначить сети провайдерам и при необходимости провайдера по умолчанию. **Пока настройки сетей и default не заданы, новые регистрации будут получать 404**. Ранее выданные токены действуют до обычного окончания/отзыва сессий.
7. Проверить:
   ```sh
   curl -i https://start.iptv.artelmik.ru/api/v1/client/discover
   curl -i https://start.iptv.artelmik.ru/api/v1/client/bootstrap
   ```
   Проверяйте со внешнего клиентского IP (из нужной сети), а не только с localhost — результат зависит от источника!

## Безопасность/ограничения

- Определение IP выполняется по `req.socket.remoteAddress`, а `X-Real-IP` принимается **только при подключении с loopback** (локальный доверенный nginx). Клиентский `X-Forwarded-For` не используется.
- Адрес клиента приводится из IPv4-mapped IPv6 (`::ffff:x.x.x.x`) к IPv4 для сопоставления.
- Выделенные подсети предназначены для определения провайдера, а не для абонентской авторизации. Доступ к платным каналам всё равно требует обычный логин и токен.
- Мобильные пользователи могут прийти из сотовой сети, не принадлежащей провайдеру. Для них удобно задать провайдера по умолчанию; в многопровайдерной системе может потребоваться отдельный процесс выбора вне IP, который будет согласован отдельно.
- Переопределение провайдера по обнаружению может инициировать новую регистрацию устройства и повлиять на лимит терминалов. Сервер не перекидывает существующего подписчика между провайдерами автоматически.
- Новый URL должен быть доступен по HTTPS и не должен перенаправлять на старый портал.
