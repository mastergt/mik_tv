# IPTV Control — этап 2: «Абоненты» и «Терминалы» (v0.3.0)

Обновление **поверх уже запущенного IPTV проекта**. Использует существующую БД `iptv_front` и порт API `4012`. Не затрагивает `iptv_dev` и не содержит SQL-миграций: все используемые таблицы уже созданы миграцией `0003_subscribers`.

## Установка

Обновляйте из корня проекта, где лежат каталоги `backend/` и `frontend/`:

```bash
cd /usr/local/nodejs/dev/iptv_front
cp -a backend backend.before-subscribers
cp -a frontend frontend.before-subscribers
unzip -o /path/to/iptv-subscribers-terminals-v0.3.0.zip
```

В `backend/.env` **добавьте одну переменную**, не переписывая остальные:

```dotenv
ABONENT_PASSWORD_KEY=<64 hex-символа>
```

Для генерации значения:

```bash
openssl rand -hex 32
```

Ключ AES-256-GCM используется для возможности *показывать* пароль абонента сотруднику с отдельным разрешением `abonents.credentials.read`. Одновременно сохраняется Argon2id-хеш для будущей авторизации абонента. Не меняйте и не теряйте этот ключ: старые зашифрованные пароли без него нельзя будет восстановить. Резервную копию храните отдельно от SQL-дампа. Если пароль абонента не задаётся, ключ не требуется для создания записи.

После обновления:

```bash
cd /usr/local/nodejs/dev/iptv_front/backend
npm run check
npm run build
pm2 restart iptv-admin-api --update-env

cd ../frontend
npm run check
npm run build
# при разработке: npm start
```

Если API запущен не через PM2, перезапустите его вашим обычным способом. Команда PM2 подразумевает имя процесса `iptv-admin-api` — уточните через `pm2 list`, если у вас оно отличается. При `pm2 restart --update-env` убедитесь, что процесс загружает правильный `.env`.

Разработка через SSH-туннель: `ssh -N -L 4200:127.0.0.1:4200 user@server`. Angular 4200, NestJS 4012, proxy `/api/v1` остаётся прежним.

## Что сделано

**Абоненты:** список с серверной пагинацией и поиском, создание/изменение, лимит терминалов и просмотров, карточка с балансом из внешнего биллинга, дата синхронизации, назначение/отзыв плейлистов и отдельных потоков с ограничением срока доступа. Пароль не возвращается в CRUD, просмотры пароля отдельно авторизуются и заносятся в `audit.events`.

**Терминалы:** список с серверной пагинацией, модель/производитель/платформа/User-Agent/IP, UUID, привязка к абоненту, включение и выключение, история авторизаций, отзыв сессии, история просмотров при наличии прав и включенном журналировании, чтение настроек и избранного по API.

**Права:** используются существующие `abonents.read/write`, `abonents.credentials.read`, `terminals.read/write`, `playback.read`, включая ограничения по провайдерам. Не требуется менять роли или миграции.

**Производительность:** страницы по умолчанию загружают 50 записей, максимум 200. Весь список из 60 000 абонентов в браузер не выгружается. Запросы поиска используются по мере ввода после паузы 350 мс. Подробная история просмотров остаётся опциональной и не запускает сбор данных сама по себе.

## API

| Метод | Адрес | Описание |
|---|---|---|
| GET | `/api/v1/abonents?providerId=1&search=...&limit=50&offset=0` | Список с `items,total,limit,offset` |
| GET | `/api/v1/abonents/:id` | Карточка без пароля |
| POST | `/api/v1/abonents` | Создание абонента |
| PATCH | `/api/v1/abonents/:id` | Редактирование |
| POST | `/api/v1/abonents/:id/reveal-password` | Аудируемый просмотр пароля |
| GET | `/api/v1/abonents/:id/entitlements` | Назначения |
| POST | `/api/v1/abonents/:id/playlists` | Добавить плейлист |
| DELETE | `/api/v1/abonents/:id/playlists/:playlistId` | Снять плейлист |
| POST | `/api/v1/abonents/:id/streams` | Добавить отдельный поток |
| DELETE | `/api/v1/abonents/:id/streams/:streamId` | Снять поток |
| GET | `/api/v1/terminals` | Терминалы с фильтрами |
| GET | `/api/v1/terminals/:id` | Карточка терминала |
| POST | `/api/v1/terminals` | Ручная регистрация (для администрирования/тестов) |
| PATCH | `/api/v1/terminals/:id` | Привязка, название, блокировка |
| GET | `/api/v1/terminals/:id/sessions` | Последние 100 авторизаций |
| POST | `/api/v1/terminals/:id/sessions/:sessionId/revoke` | Отзыв сессии |
| GET | `/api/v1/terminals/:id/playback` | Последние 100 просмотров |
| GET | `/api/v1/terminals/:id/settings` | Персональные настройки |
| GET | `/api/v1/terminals/:id/favorites` | Избранные каналы |

Для назначения потока или плейлиста тело:

```json
{"item_id":"15","enabled":true,"valid_until":"2026-12-31T23:59:59+03:00"}
```

`valid_until` необязателен, тогда доступ не имеет конечного срока. Возможна повторная выдача уже назначенного ресурса (`UPSERT`). Ограничения доступа провайдера проверяются как в NestJS, так и существующим триггером PostgreSQL.

Для создания абонента:

```json
{"provider_id":1,"username":"contract-123","display_name":"Тестовый абонент","contract_number":"123","enabled":true}
```

Пароль можно задать дополнительно полем `password`; минимум шесть символов. Для абонентов, которые будут авторизоваться через внешнюю систему, локальный пароль необязателен.

## Проверка API

```bash
curl -i http://127.0.0.1:4012/api/v1/health
# Должен быть HTTP 200.

curl -i http://127.0.0.1:4012/api/v1/abonents
# Без JWT должен быть HTTP 401, а не HTTP 500.
```

После входа в Angular откройте разделы «Абоненты» и «Терминалы». Проверяйте CRUD и права под суперадминистратором и отдельно под пользователем, ограниченным одним провайдером.

## Известные ограничения этапа

- Клиентское Android API регистрации устройств и реальная авторизация абонентов ещё не реализованы. Поэтому таблица терминалов пока будет заполняться только вручную или будущими внешними интеграциями.
- Ограничение одновременного воспроизведения требует отдельного механизма runtime-lease (например, Redis); поле лимита пока лишь хранится.
- История воспроизведений не генерируется сама по себе: она начнёт наполняться клиентским API, когда оно появится.
- Автоматическая синхронизация баланса с внешним биллингом ещё не реализована.
- Каталог назначаемых плейлистов в интерфейсе загружает до 200 записей; более крупным каталогам позже потребуется поиск с сервера.
- Подробную EPG-админку реализуем следующим этапом.

## Проверки поставки

Синтаксис исходного TypeScript проверяется статически. Полная проверка `npm run check`, Angular build и интеграция с реальным PostgreSQL должна выполняться на DEV-сервере пользователя, где установлены npm-зависимости и БД.
